# KCMPS Storefront — Asset Bucket Structure & Manifest

This is the folder convention and manifest-generation plan for the **private product-image
S3 bucket** served via CloudFront with Origin Access Control (OAC) — the bucket referenced
in the root `CLAUDE.md`'s auth/infra notes, separate from the `website/` deploy bucket.
Nothing in this doc is deployed yet; it's the plan `website/index.html`'s hero carousel is
already written against (see `HERO_MANIFEST_URL` in that file's carousel script), the same
"build the frontend against the target shape, swap the source later" pattern used
throughout this repo (`store.js` → `KCMPS_STORE`, `dashboard-data.js` → `KCMPS_DASH`).

---

## 1. Folder convention

One prefix per shop category, matching the three business pillars (Print, Studio Design,
Hardware Merch) plus the Office Supplies sub-line under Print:

```
/assets/printing-office-supplies/<sku-or-slug>/<image-files>
/assets/design/<sku-or-slug>/<image-files>
/assets/merch/<sku-or-slug>/<image-files>
```

- `<sku-or-slug>` should match (or be derivable from) the `id` used in
  `website/products.js`, so a future catalog-image lookup doesn't need its own mapping
  table — `sku-or-slug` *is* the join key.
- Each sku folder holds one or more images for that product.

**Category → pillar mapping** (for whoever is uploading, since `products.js`'s `leaf` keys
are finer-grained than these three prefixes):

| Prefix | Pillar | Covers these `products.js` leaves |
|---|---|---|
| `printing-office-supplies` | Print Production + Office Supplies | `print-office` |
| `design` | Studio Design (apparel/DTF, plus the rest of the design catalog) | `dtf`, `subli`, `hotmelt`, `3dprint`, `souvenir` |
| `merch` | Hardware Merch | `network`, `storage` |

This matches the tab structure in `website/index.html` (`panel-design` contains Apparel/DTF,
Subli, Hotmelt, 3D Print, and Souvenir as sub-tabs; `panel-merch` contains Network and
Storage) and the `CATEGORY_TO_LEAF`/`PAGE_VARIANTS` mapping in the hero-priming script. The
`entertainment` leaf was removed from the catalog entirely — KCMPS doesn't sell audio/gaming
gadgets — so it no longer appears here either.

### Primary vs. gallery image naming

Within a sku folder, the **first display image** (catalog thumbnail, and the only image
type the hero carousel pool draws from — see §3) is always named with a `01-main` *prefix*
(not necessarily the exact bare filename); everything else is numbered gallery overflow:

```
/assets/merch/wireless-earbuds/01-main.jpg                       ← primary / thumbnail / hero-eligible
/assets/design/mobile-legends/01-main-MOBILE LEGENDS SHIRT.jpg   ← also valid — prefix + original filename kept as a
                                                                      suffix for traceability back to the source art file
/assets/merch/wireless-earbuds/02.jpg                             ← gallery
/assets/merch/wireless-earbuds/03.jpg                             ← gallery
```

Keeping the original filename as a suffix (rather than discarding it once slugged into the
folder name) is deliberate — see `website/assets/design/*/01-main-*` for 33 real examples
from the DTF design archive, where the original creative-file names (e.g. artist/character
references) needed to stay traceable for future investigation, not just the slug.

Rules:
- Exactly one file starting with `01-main` per sku folder. The manifest generator (§2)
  treats the first filename matching `01-main*` as the primary image; if none match, it
  falls back to the alphabetically-first file in the folder (logged as a warning, not a
  hard failure — an uploader forgetting the `01-main` prefix shouldn't take the sku out of
  the catalog).
- Extensions: `.jpg` or `.png`. Keep gallery files zero-padded two-digit (`02.jpg`, not
  `2.jpg`) so they sort correctly when listed.

## 2. Manifest generation

**Frontend never calls `ListObjectsV2` on the bucket at request time** — that's slower and
more expensive per-request than serving one cached JSON file from CloudFront, and it's the
same "fetch a JSON index, don't enumerate a data source live" pattern used for the catalog
(`products.js`) and dashboard mock data.

Instead, `/assets/manifest.json` (root of the same bucket, served through the same
CloudFront distribution) is regenerated by an S3-event-triggered Lambda —
`logic-inputs/generate-asset-manifest.js` — every time an object under `/assets/<category>/`
is created or removed:

```
S3 (ObjectCreated:*, ObjectRemoved:* on prefix "assets/")
        │
        ▼
generate-asset-manifest.js  (Lambda, Node.js 20.x)
  1. ListObjectsV2 across the three category prefixes
  2. Group keys by <category>/<sku>/
  3. Pick the primary image per sku (§1's 01-main rule)
  4. Write assets/manifest.json back to the same bucket
        │
        ▼
(optional) CloudFront invalidation for /manifest.json only
```

No CI/CD step is required for this to work — S3 event notifications fire on every upload
regardless of how the file got there (console, CLI, a future CI/CD pipeline), so "upload an
image to the right folder" is the entire authoring workflow. A CI/CD-triggered rebuild is
also fine if the team prefers deploying images as part of a pipeline; the Lambda's logic
would be identical either way, just invoked from a different trigger.

### 2.1 IAM

- `s3:ListBucket`, `s3:GetObject` scoped to the assets bucket ARN.
- `s3:PutObject` scoped to `arn:aws:s3:::<bucket>/manifest.json` only (least privilege —
  this Lambda writes exactly one object).
- `cloudfront:CreateInvalidation` scoped to the distribution ARN, only if invalidation is
  wired in (optional — `manifest.json` can also just be served with a short
  `Cache-Control max-age`, e.g. 5 minutes, so staleness self-heals without needing
  invalidation at all; simpler to operate, pick this by default).

## 3. Manifest shape

```json
{
  "generatedAt": "2026-07-25T03:00:00Z",
  "categories": {
    "printing-office-supplies": [
      {
        "sku": "business-cards",
        "featured": true,
        "primary": "assets/printing-office-supplies/business-cards/01-main.jpg",
        "images": [
          "assets/printing-office-supplies/business-cards/01-main.jpg",
          "assets/printing-office-supplies/business-cards/02.jpg"
        ]
      }
    ],
    "design": [],
    "merch": [
      {
        "sku": "wireless-earbuds",
        "featured": false,
        "primary": "assets/merch/wireless-earbuds/01-main.jpg",
        "images": [
          "assets/merch/wireless-earbuds/01-main.jpg",
          "assets/merch/wireless-earbuds/02.jpg",
          "assets/merch/wireless-earbuds/03.jpg"
        ]
      }
    ]
  }
}
```

- `featured` — staff-set flag (there's no admin UI for this yet; until one exists, set it
  by hand in the sku's source, or treat it as an S3 object tag on `01-main` that the Lambda
  reads — either is a small addition to `generate-asset-manifest.js`, not a manifest-shape
  change). Hero-eligible pool building rule: see §3 of the hero carousel behavior, below.
- `images` always includes `primary` as its first element, so a consumer that only wants
  "the" image for a sku can just take `images[0]` and ignore the `primary` field if
  preferred — both are kept for clarity at call sites.
- Empty categories (like `design` above, before any design-service photography exists) are
  valid — always present as an array, never omitted, so frontend code can iterate
  `Object.values(manifest.categories)` unconditionally.

## 4. How the frontend consumes this

`website/index.html`'s hero carousel fetches this file (`HERO_MANIFEST_URL` constant near
the carousel script) and builds its rotation pool from every sku's `primary` image only
(not full galleries — the hero is about cross-category exposure, one photo per product, not
a product detail gallery). See that file's inline comments for the shuffle/persistence
logic. A future catalog-page image lookup would instead want the full `images` array per
sku — same manifest, different consumer, no shape change needed.

## Acceptance criteria

- Uploading a new image to the correct S3 folder (with `01-main` naming) and re-running the
  manifest step makes it eligible for the hero carousel with zero frontend code changes.
- No image repeats in the hero rotation until every image in the pool has been shown at
  least once (enforced client-side — see the shuffle logic in `website/index.html`).
